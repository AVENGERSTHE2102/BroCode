# Waypoint

Waypoint is an action-first connected-data agent with shared workflow packs for fraud investigation, security triage, and codebase work. It uses graph relationships and MCP tools to produce explainable, source-backed recommendations; GitHub and cloud deployment actions require human approval and verified outcomes. Agents That Act on Connected Data is the primary track; Company Brain and Agent Memory and Coordination support all three workflows.

## Current implementation

The app now has Supabase-backed sign-in scaffolding, workspace membership checks, per-workspace FalkorDB graph routing, and an authenticated MCP endpoint at `/api/mcp`. The endpoint supports stateless MCP `2026-07-28` discovery, tools, three workflow prompt templates, and the prior initialize handshake; SDK interoperability still needs a live conformance check. MCP offers graph/evidence reads, quarantined fact candidates for owner/admin review, task coordination, run traces, and human-review action proposals. Candidate values stay out of trusted facts, graph projections, and run traces until approved; direct current-fact writes are disabled. Owners/admins can execute an approved GitHub patch as a draft pull request; it is bound to the exact approved hash and fresh evidence, uses a short-lived single-repository write token, and never merges. The API/migration/provider behavior is not live-verified. An investigation API can use an OpenAI-compatible model to select from the MCP tools, but it is not live until provider credentials and connected source data are configured. GitHub connection/import code includes repository records and optional Dependabot alerts using a separate single-repository read token; alerts and revisions are owner/admin-only. GitHub marks its Dependabot alerts REST API as public preview and subject to change. Migrations and live runtime behavior remain unverified. Cloud deployment and fraud-case imports remain open.

To check FalkorDB from the local Mac/Node environment used to run Next.js, run `bun run diagnose:falkordb` from the repository root in normal macOS Terminal. The diagnostic reads the existing `.env.local`, reports only the endpoint hostname/port/protocol and check statuses, and performs DNS, TCP, TLS certificate validation, Redis authentication, then a read-only `PING`. It never prints credentials or changes database data. This checks the local runtime context; if the app is deployed remotely, run the same diagnostic in that host's Node runtime before treating it as application-runtime evidence. M1.2 remains unverified until authenticated `PONG` succeeds from the actual application runtime.

The workspace home includes a read-only Ask form backed by `POST /api/ask`; it creates a durable investigation, runs the shared agent with proposals, fact candidates, and task updates disabled, and leaves a link to inspect the trace or retry. The investigation screen also supports follow-up questions through `POST /api/investigations/{id}/run`. It requires server-only `AI_BASE_URL`, `AI_API_KEY`, and `AI_MODEL` settings for an OpenAI-compatible `/chat/completions` API. The model receives MCP tool schemas; each tool call is workspace-authorized, scoped to the selected investigation, and added to its run trace. Factual answers must use structured claims with source/version citations returned by authorized graph reads; malformed answers or unsupported citations abstain. The UI displays uncertainty and verified citations. State-changing task and memory tools are exposed only for explicit user intents; `remember_fact` submits a quarantined candidate for owner/admin review, and only approved facts enter current memory and graph retrieval. Action proposals require source/version pairs returned by an earlier tool call. The endpoint returns 503 when model settings are absent; no model credentials are currently configured in this workspace.

To compare the graph agent, text retrieval, and Markdown-memory baseline on the checked-in synthetic fixtures, configure the same `AI_BASE_URL`, `AI_API_KEY`, and `AI_MODEL`, then run `bun run eval:compare`. It reports per-mode input bytes, provider token usage when available, reference-path coverage, abstention matches, lexical claim overlap, and failed case IDs; claim overlap is a weak proxy, not semantic scoring. The default budget is 32,000 cumulative serialized request bytes and 1,800 output tokens per case/mode; adjust with `AI_EVAL_CONTEXT_BUDGET_BYTES` or limit a smoke run with `AI_EVAL_MAX_CASES=1`. Results are printed to stdout, are synthetic-only, and model calls may incur provider usage charges. They do not satisfy real-corpus acceptance.

Workspace owners/admins can connect and sync a repository from the home page using the read-only GitHub App integration. Configure `GITHUB_APP_ID`, `GITHUB_APP_SLUG`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_APP_CLIENT_ID`, `GITHUB_APP_CLIENT_SECRET`, and a random `GITHUB_APP_STATE_SECRET` of at least 32 characters as server-only secrets. Set the App's callback URL to `<application-origin>/api/sources/github/callback` and enable user authorization during installation. Grant `Metadata`, `Contents`, `Issues`, `Pull requests`, and `Checks` read permissions for source sync. To enable reviewed draft PR creation, also grant `Contents` and `Pull requests` write plus `Commit statuses` read; normal listing/import tokens remain limited to read-only permissions. Install only on repositories the workspace may expose. OAuth state is signed and bound to the authenticated Waypoint workspace/user; the callback verifies the installation is associated with the authorizing GitHub user before binding it to that workspace. Tokens are restricted to one selected repository and revoked after each request. Sync imports up to 200 commits, issues, and pull requests, 500 file metadata records, and 100 check runs for the default-branch head, without reading file contents. For the first 10 returned pull requests, it also imports up to 20 changed-file paths each and projects `PullRequest -[:CHANGED_FILE]-> File`; partial reads are reported and do not replace the last complete path set. Check runs retain their source version and project as `Commit -[:HAS_CHECK_RUN]-> CheckRun` evidence. An owner/admin can approve a displayed patch and separately click **Create draft pull request**; before execution the service verifies exact proposal hash, approval age (24 hours), current repository evidence versions, and pinned base branch SHA. It creates a deterministic proposal branch and a draft PR, verifies the resulting PR head/base/check state, and never merges. Retries reconcile the same branch and PR. The reviewed diff, rationale, and risk are sent to GitHub as approved PR content. Apply every migration in `supabase/migrations` in filename order through `202610150021_investigation_workflow_domains.sql`. New investigations select a fraud, security, or codebase workflow; live source connectors and evidence still determine whether each workflow can answer. Live GitHub, Supabase, and FalkorDB behavior remains unverified.
Owners/admins can also add reviewed aliases in the workspace. An alias is bound to exactly one verified entity; conflicts are rejected. MCP resolution tries exact IDs first, then the explicit alias table, and returns ambiguous candidates without treating ambiguous matches as evidence. Migration `202610150011_workspace_entity_aliases.sql` is included in the ordered migration sequence above.

## Run

```sh
bun install
cp .env.example .env.local
# Set the managed Supabase project URL/key and FalkorDB Cloud TLS URL.
bun run dev
```

Apply the SQL migrations in `supabase/migrations` to the managed Supabase project in filename order. Configure the Supabase auth site URL and callback URL for the application origin. Configure your host scheduler to run `bun run worker:graph-projection` with `SUPABASE_SERVICE_ROLE_KEY` and `FALKORDB_URL` available only to the server. No Docker is used.
