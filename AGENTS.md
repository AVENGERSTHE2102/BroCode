# Repository instructions

Before working on Waypoint, read [IMPLEMENTATION_TRACKER.md](IMPLEMENTATION_TRACKER.md) and [TESTING.md](TESTING.md). The tracker is the source of truth for delivery scope, dependencies, decisions, blockers, and completion evidence. TESTING.md is the runbook for getting a clean checkout running and verified — follow it before claiming anything works.

After meaningful implementation or verification, update the tracker before ending the work session. Mark an item `done` only when its acceptance criteria have supporting evidence — see TESTING.md §5 for what counts as which level of evidence. Record blockers and the next action for incomplete work, and continue independent work that does not depend on the blocker. Do not store credentials or secret values in the tracker or repository.

Product constraints: Agents That Act on Connected Data is the primary track; Company Brain and Agent Memory and Coordination must support the same real engineering workflow. Prefer cloud-hosted databases and services for anything that ends up in a deployed/judged environment. **Local Docker is allowed and currently necessary for FalkorDB**: the configured FalkorDB Cloud endpoint has been unreachable (`ENOTFOUND`) since at least 2026-10-15, so local development uses a Docker FalkorDB container (see TESTING.md §2.2) until that's resolved or a working cloud endpoint is reconfigured. Don't silently revert to a cloud-only assumption — verify the cloud endpoint actually resolves before relying on it. Synthetic records are allowed for automated tests, but do not count as proof of real integration or product acceptance. Agents may propose actions; a human must approve before execution.

Use Bun 1.3.9 as the package manager. Keep `bun.lock` committed and do not regenerate or commit npm/yarn/pnpm lockfiles. Use `bun install`, `bun add`/`bun remove`, and `bun run <script>`.
